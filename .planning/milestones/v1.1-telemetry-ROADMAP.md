# Roadmap: Telemetrie & Wirksamkeitsanalyse

## Overview

Dieses Milestone baut ein zentrales Reporting-System für den EEG Energy Optimizer. Anonymisierte Telemetriedaten von opt-in HA-Installationen fließen in ein eigenes Cloudflare-Backend, das Diagnose und Wirksamkeitsanalyse ermöglicht — ohne monatliche Kosten und ohne Personenbezug.

**Datenstrategie:** State-Change-Events (sofort, ausführlich) + 30-min-Snapshots (schlank, gebündelt 1×/h) + Outcome-Events (am Ende eines Lade-/Entlade-Blocks) + Failure-Events (bei Fehlern).

**Identität:** UUIDv4 pro Anlage, kein Nahbereich-ID-Konzept, kein Personenbezug.

**Auth:** Bootstrap-Token (im HACS-Release) für Erstregistrierung, danach pro Anlage individueller `api_key` (Bearer).

**Stack:** Cloudflare Workers + D1 (SQLite) + R2 (Cold Storage) + Pages + Cloudflare Access — alles im Free Tier.

**Skalierungsgrenze (Free Tier):** mit smarter Sende-Strategie tragfähig für ~1.700 Anlagen.

## Phases

- [ ] **Phase 1: Backend-Skelett (Cloudflare)** — Worker, D1-Schema, R2-Bucket, alle Event-Endpoints, Bootstrap- + Bearer-Auth
- [ ] **Phase 2: HA Reporter-Modul** — UUID-Verwaltung, Event-Queue, 30-min-Timer, Decision-Refactor mit `reasons`/`blocked_by`, Opt-in im Panel
- [ ] **Phase 3: Dashboard** — Cloudflare Pages SPA mit Cloudflare Access, 4 MVP-Views
- [ ] **Phase 4: Sicherheit & Pflege** — Rate-Limits, DELETE-Endpoint, Daten-Rotation D1→R2, Privacy-Doku

## Phase Details

### Phase 1: Backend-Skelett

**Ziel:** Cloudflare Worker nimmt Events entgegen und speichert sie strukturiert. Kein Dashboard, keine Reads.

**Repository:** `eeg-telemetry-backend` (neues, separates Repo — nicht dieses hier)

**Stack:** Wrangler CLI, Worker (TypeScript), D1, R2.

**Success Criteria:**
1. `POST /v1/register` mit korrektem Bootstrap-Token gibt `installation_id` + `api_key` zurück und legt einen Eintrag in D1 an
2. Alle Event-Endpoints (`/v1/snapshot`, `/v1/state-change`, `/v1/outcome`, `/v1/failure`, `/v1/profile`) akzeptieren Bearer-`api_key` und schreiben in die jeweilige D1-Tabelle
3. `DELETE /v1/installation` löscht alle Daten dieser Anlage aus allen Tabellen und R2
4. IP-Rate-Limit auf `/v1/register` (5/h) und Per-Installation-Rate-Limit (200/h) greifen, beide via Workers KV
5. Cron-Worker nightly aggregiert `snapshots` + `state_changes` + `outcomes` des Vortags in `daily_aggregates` und rotiert `snapshots` älter als 14 Tage nach R2

**D1-Schema:** siehe Anhang A.

**Worker-Endpoints:**

| Methode | Pfad | Auth | Zweck |
|---------|------|------|-------|
| POST | `/v1/register` | `X-Bootstrap-Token` Header | Anlage registrieren, gibt UUID + api_key zurück |
| POST | `/v1/snapshot` | Bearer api_key | Snapshot annehmen (Array erlaubt) |
| POST | `/v1/state-change` | Bearer api_key | State-Change-Event |
| POST | `/v1/outcome` | Bearer api_key | Outcome-Event |
| POST | `/v1/failure` | Bearer api_key | Failure-Event |
| POST | `/v1/profile` | Bearer api_key | Settings/Version-Update |
| DELETE | `/v1/installation` | Bearer api_key | Recht auf Vergessen |

**Cron-Worker (nightly 02:00 UTC):**
- Aggregiert Vortag in `daily_aggregates`
- Rotiert Snapshots > 14 Tage nach R2 als `snapshots/{installation_id}/{YYYY-MM-DD}.ndjson.gz`
- Löscht rotierte Snapshots aus D1
- Löscht `installations` ohne `last_seen_at`-Update seit 90 Tagen

**Deliverables:**
- Repo `eeg-telemetry-backend` mit `wrangler.toml`, `migrations/0001_init.sql`, `src/worker.ts`, `src/cron.ts`, README
- Deploys nach `eeg-telemetry.<eigene-domain>.workers.dev`
- D1- und R2-Bindings konfiguriert
- Bootstrap-Token als `wrangler secret`

### Phase 2: HA Reporter-Modul

**Ziel:** Integration kann Anlage registrieren und Events senden. Opt-in im Panel.

**Repository:** dieses (`HA_EEG_Energy_Optimizier`)

**Depends on:** Phase 1 deployed

**Success Criteria:**
1. Opt-in-Toggle im Panel registriert die Anlage einmalig und speichert `installation_id` + `api_key` via `homeassistant.helpers.storage.Store` (NICHT im Config Entry)
2. State-Change-Events werden sofort gesendet, mit strukturierter `reasons`/`blocked_by`-Liste aus dem refactorierten `Decision`-Dataclass
3. 30-min-Timer schreibt Snapshots in eine lokale Queue, sendet sie alle 60 min als Batch
4. Outcome-Events werden beim Übergang Morgen-Einspeisung/Abend-Entladung → Normal gesendet, inklusive predicted-vs-actual aus den Forecast-Sensorwerten zum Block-Start
5. Failure-Events werden bei Inverter-Write-Fehler, Forecast-Provider-Fehler und Sensor-Unavailability >10 min gesendet
6. Bei Backend-Unerreichbarkeit puffert der Reporter bis zu 100 Events lokal und sendet sie bei Reconnect
7. Opt-out-Button löscht alle Daten via `DELETE /v1/installation` und entfernt UUID/key lokal

**Neue Dateien:**
- `custom_components/eeg_energy_optimizer/telemetry.py` — `TelemetryReporter`-Klasse (UUID, HTTP, Queue, Retry)
- `custom_components/eeg_energy_optimizer/telemetry_buffer.py` — persistente Storage-Wrapper

**Touched Files:**

- `optimizer.py` — `Decision` um `reasons`/`blocked_by`/`snapshot` erweitern, `_should_*` liefern Tupel `(bool, list[str], list[str])` zurück
- `statistics.py` — Outcome-Event triggern bei Block-Ende
- `const.py` — `CONF_TELEMETRY_ENABLED`, `STORAGE_TELEMETRY`, `TELEMETRY_BACKEND_URL`, `TELEMETRY_BOOTSTRAP_TOKEN`
- `websocket_api.py` — 4 neue Commands: `telemetry/get_status`, `telemetry/enable`, `telemetry/disable`, `telemetry/forget`
- `frontend/eeg-optimizer-panel.js` — Sektion „Community-Statistik": Toggle, Status, Recht-auf-Vergessen
- `translations/de.json`, `en.json`
- `manifest.json` — Version-Bump

### Phase 3: Dashboard

**Ziel:** Web-UI zum Lesen der Telemetriedaten, geschützt durch Cloudflare Access.

**Repository:** `eeg-telemetry-backend` (im Unterordner `dashboard/`)

**Depends on:** Phase 2 läuft mit echten Daten

**Success Criteria:**
1. Cloudflare Pages serviert die SPA, Cloudflare Access mit Email-OTP erlaubt nur Allowlist-Zugriff
2. Worker liefert `GET /v1/stats/...` JSON, prüft `CF-Access-Jwt-Assertion`
3. View „Übersicht" listet alle Anlagen mit `last_seen_at`, App-Version, Inverter-Typ, heutigen State-Changes
4. View „Anlagen-Detail" zeigt Zeitreihen (SOC, PV, Verbrauch) der letzten 7 Tage und State-Changes mit Reasons/Blocked-By
5. View „Forecast-Qualität" plottet predicted-vs-actual aus Outcomes, gruppiert nach Forecast-Provider
6. View „Failures" listet Fehler-Kategorien mit Häufigkeit und Anlagen-Drilldown

**Stack:** Cloudflare Pages, statisches SPA (Plain JS oder Svelte — passend zum Stil von `eeg-optimizer-panel.js`).

### Phase 4: Sicherheit & Pflege

**Ziel:** Härtung und langfristige Datenhygiene.

**Repositories:** beide

**Depends on:** Phase 1 + 2

**Success Criteria:**
1. Rate-Limiting im Worker via KV-Counter (200 req/h pro Installation, 5/h pro IP für `/register`)
2. `DELETE /v1/installation` löscht alle R2-Files mit Prefix `snapshots/{installation_id}/` zuverlässig
3. Cron-Worker löscht R2-Files älter als 2 Jahre, `daily_aggregates` älter als 5 Jahre
4. Privacy-Sektion im HA-Panel und in `README.md` dokumentiert genau, was gesendet wird, was nicht, und wie man es löscht
5. Failure-Notification: Mail an Maintainer, wenn dieselbe Failure-Kategorie für eine Anlage > X/Tag

## Anhang A: D1-Schema (Phase 1)

```sql
CREATE TABLE installations (
  installation_id        TEXT PRIMARY KEY,
  api_key_hash           TEXT NOT NULL,
  registered_at          TEXT NOT NULL,         -- Telemetrie-Opt-in
  last_seen_at           TEXT,
  revoked                INTEGER NOT NULL DEFAULT 0,
  integration_started_at TEXT,                  -- HA-Integration ursprüngliche Installation
  app_version            TEXT,                  -- EEG-Optimizer-Version
  ha_version             TEXT,                  -- Home-Assistant-Core-Version
  inverter_type          TEXT,
  battery_capacity_kwh   REAL,
  pv_peak_kwp            REAL,
  forecast_provider      TEXT,
  country_iso            TEXT,
  settings_json          TEXT                   -- ohne entity_ids!
);

CREATE TABLE snapshots (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  installation_id TEXT NOT NULL,
  ts TEXT NOT NULL,
  state TEXT, mode TEXT,
  soc_pct INTEGER,
  pv_now_kw REAL, consumption_now_kw REAL,
  grid_now_kw REAL, battery_now_kw REAL,
  min_soc_dyn INTEGER, hysteresis INTEGER
);
CREATE INDEX idx_snapshots_inst_ts ON snapshots(installation_id, ts);

CREATE TABLE state_changes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  installation_id TEXT NOT NULL,
  ts TEXT NOT NULL,
  transition TEXT NOT NULL,
  mode TEXT,
  reasons TEXT,
  blocked_by TEXT,
  snapshot_json TEXT
);
CREATE INDEX idx_state_changes_inst_ts ON state_changes(installation_id, ts);

CREATE TABLE outcomes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  installation_id TEXT NOT NULL,
  event_type TEXT,
  started_at TEXT, ended_at TEXT,
  duration_minutes INTEGER,
  grid_export_kwh REAL, peak_power_kw REAL,
  soc_start_pct INTEGER, soc_end_pct INTEGER,
  predicted_pv_kwh REAL, actual_pv_kwh REAL,
  predicted_consumption_kwh REAL, actual_consumption_kwh REAL,
  terminated_by TEXT
);
CREATE INDEX idx_outcomes_inst_started ON outcomes(installation_id, started_at);

CREATE TABLE failures (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  installation_id TEXT NOT NULL,
  ts TEXT NOT NULL,
  category TEXT, severity TEXT,
  message_hash TEXT, context_json TEXT
);
CREATE INDEX idx_failures_inst_ts ON failures(installation_id, ts);

CREATE TABLE daily_aggregates (
  installation_id TEXT NOT NULL,
  date TEXT NOT NULL,
  snapshot_count INTEGER,
  soc_min INTEGER, soc_max INTEGER, soc_avg REAL,
  state_changes INTEGER,
  morning_blocks INTEGER, morning_block_kwh REAL,
  evening_discharges INTEGER, evening_discharge_kwh REAL,
  failures INTEGER,
  PRIMARY KEY (installation_id, date)
);
```

## Anhang B: Auth-Flow

**Erstregistrierung (einmalig):**
```
HA → POST /v1/register
     X-Bootstrap-Token: <hardcoded in telemetry.py, kommt mit HACS-Release>
     Body: { app_version, inverter_type, battery_capacity_kwh, ... }

Worker:
  prüft Bootstrap-Token + IP-Rate-Limit (5/h)
  generiert installation_id (UUIDv4) + api_key (32 Byte random base64url)
  speichert installation_id, sha256(api_key), Profil

Worker → 201 { installation_id, api_key }
HA persistiert beides via Store (NICHT Config Entry)
```

**Laufender Betrieb:**
```
HA → POST /v1/<endpoint>
     Authorization: Bearer <api_key>

Worker:
  sha256(api_key) ∈ installations.api_key_hash + revoked=0
  Per-Installation-Rate-Limit (200/h)
  schreibt Event, updated last_seen_at

Worker → 204
```

## Anhang C: Sende-Frequenz pro Anlage/Tag

| Event | Frequenz | Volumen |
|-------|----------|---------|
| Snapshots | 48/Tag, gebündelt 1×/h | ~24 Requests/Tag |
| State-Changes | ~2-6 / Tag | sofort |
| Outcomes | ~2-4 / Tag | nach Block-Ende |
| Failures | 0 - selten | bei Auftreten |
| Profile-Update | nur bei Settings-Change | ~0/Tag |

→ ~30 Requests/Tag/Anlage. Free Tier (100k/Tag) trägt ~3.300 Anlagen.

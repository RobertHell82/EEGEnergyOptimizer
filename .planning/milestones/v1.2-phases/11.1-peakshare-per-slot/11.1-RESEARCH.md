### Implementierungs-Hinweise (User-locked)

- `_evaluate_slot_a` und `_evaluate_slot_b` müssen vor der Fixzeit-Window-Prüfung einen PeakShare-Plan-Lookup machen und — falls vorhanden — den PeakShare-Sub-Fenster-Bereich als Aktivierungs-Window verwenden.
- Slot-A-Reserve-Aufschlag (`min_soc + a_reserve_pct`) bleibt unabhängig vom Window-Modus erhalten.
- Pro-Slot-Hysterese (`_slot_a_activated_date`, `_slot_b_activated_date`) bleibt erhalten.
- Der bereits existierende Cache `_discharge_plan: dict[a/b]` wird endlich mit Slot-B-Plänen befüllt.
- Default-Wechsel `discharge_a_reserve_pct` 15 % → 5 % ist Verhaltensänderung — Bestands-Anlagen behalten ihren konfigurierten Wert (kein Migration-Override; existierende User-Setups mit explizitem 15 % bleiben unverändert).

## Summary

Phase 11.1 ist eine **gezielte Implementierungs-Lücke** der bereits vorhandenen Phase-11-Infrastruktur: Plan 11-02 hat den PeakShare-Cache-Schema-Wechsel von `tuple` auf `dict[Literal["a","b"], tuple|None]` durchgezogen und `get_discharge_plan(...)` um den keyword-only `slot=`-Parameter inkl. `window_start`/`window_end`-Overrides erweitert (`peakshare.py:308-432`). Plan 11-04 hat dann aber NICHT — wie ursprünglich versprochen — die zwei Aufruf-Stellen in `_evaluate_slot_a` und `_evaluate_slot_b` nachgereicht. Stattdessen entscheiden beide Slot-Evaluatoren heute nur über Fixzeit + SOC + Hysterese, und PeakShare wirkt ausschließlich im Legacy-Single-Window-Pfad (`_evaluate_legacy_window` Z. 1346-1373).

Phase 11.1 schließt diese Lücke mit nur drei kleinen, gut abgegrenzten Änderungen:
1. **`_evaluate_slot_a`** bekommt einen vorgelagerten PeakShare-Lookup mit Window-Grenzen `[a_start, a_end_cap]` (wobei `a_end_cap = b_start − 5min` wenn Slot B aktiv, sonst `compute_hard_cutoff`).
2. **`_evaluate_slot_b`** bekommt einen vorgelagerten PeakShare-Lookup mit Window-Grenzen `[b_start, compute_b_window_end(...)]`.
3. **`DEFAULT_DISCHARGE_A_RESERVE_PCT`** wird in `const.py` von `15` auf `5` gesenkt (`setdefault`-Migration berührt Bestands-User nicht).

Der Algorithmus, die Datenstrukturen und der Cache-Lifecycle sind alle schon vorhanden (`_discharge_plan` ist dict, `find_discharge_window` nimmt beliebige `window_start`/`window_end`, der Tageslock `_discharge_plan_date` ist gemeinsam für beide Slots). Phase 11.1 ist damit primär eine **Verdrahtungs-Phase** plus ein einzelner Default-Wechsel — keine neuen Konstanten, keine Migration v15→v16, keine Schema-Änderungen.

**Primary recommendation:** Plan in 2 Plans aufteilen:
1. **11.1-01** — Default-Change `15 → 5` in `const.py`, plus PeakShare-Aufruf in `_evaluate_slot_a` + `_evaluate_slot_b`, plus Mutual-Exclusion-Clamp in `_evaluate_slot_a` (Slot-A-Plan-Ende ≤ `b_start − 5min`). Tests: erweitert `tests/test_dual_window.py` um `TestPeakShareSlotIntegration`-Klasse.
2. **11.1-02** — End-to-End-Integration (Decision.discharge_window_start/end im Dual-Mode, `_discharge_detail_status` mit Slot-Plan-Lookup, Markdown-Renderer mit PeakShare-Marker pro Slot). Activity-Log-Heartbeat zeigt Slot+PeakShare-Status. Test in `tests/test_dual_window_integration.py`.

11.1-01 ist die Kern-Änderung; 11.1-02 ist Polish + UI-Konsistenz. Tests in beiden Plans sind unit + integration.

## PeakShare-API-Surface (Internals)

### `find_discharge_window` (`peakshare.py:44-131`)

**Signatur:**
```python
def find_discharge_window(
    hours: list[dict],            # Community-Forecast-Daten (timestamp + deficitKwh)
    available_kwh: float,         # Batterie-Energie für Slot
    discharge_power_kw: float,    # Konfigurierte Entladeleistung
    window_start: datetime,       # Frühester erlaubter Start (TZ-aware!)
    window_end: datetime,         # Spätestes erlaubtes Ende (TZ-aware!)
    jitter_minutes: int,          # Pre-Roll für heute (-60..+60)
) -> tuple[datetime, datetime] | None
```

**Algorithmus-Details:**

| Schritt | Verhalten | Code-Anker |
|---------|-----------|-----------|
| `required_hours` | `max(1, math.ceil(available_kwh / discharge_power_kw))` — wieviele 1h-Blöcke gebraucht werden | Z. 74 |
| Eligibility-Filter | Behält **alle** Stunden im `[window_start, window_end)` (auch `deficit=0`!) — wichtig für Contiguity | Z. 76-90 |
| Sliding-Window | Sucht den `required_hours`-Block mit höchster Deficit-Summe; **Hours müssen exakt 1h auseinander liegen** (`_is_contiguous`) | Z. 100-118 |
| Jitter-Anwendung | `start_time = best_start + timedelta(minutes=jitter)`; clamp auf `≥ window_start` | Z. 122-125 |
| End-Time-Clamp | `end_time = start_time + timedelta(hours=required_hours)`; clamp auf `≤ window_end` (HARD CUTOFF) | Z. 126-129 |
| `None`-Fälle | `available_kwh ≤ 0`, `discharge_power_kw ≤ 0`, `len(eligible) < required_hours`, kein contiguous-Block | Z. 71-72, 92-93, 119-120 |

**Key insight für Phase 11.1:** Der **End-Time-Clamp auf `window_end` ist die Mutual-Exclusion-Garantie**. Wenn wir `window_end = b_start − timedelta(minutes=5)` setzen, kann `find_discharge_window` per Konstruktion **niemals** einen Slot-A-Plan zurückgeben, der über `b_start − 5min` hinausreicht — das ist der Inverter-Race-Schutz, der hierdurch automatisch erzwungen wird.

### Jitter-Mechanik (`peakshare.py:283-306`)

| Property | Value |
|----------|-------|
| Range | `random.randint(-60, 60)` Minuten |
| Roll-Frequenz | Einmal pro Tag (per `_jitter_date`-Vergleich) |
| Persistenz | `Store` (HA-helpers.storage) — überlebt HA-Restart innerhalb desselben Tages |
| Anwendung | Auf `start_time` ADDIERT, dann clamp auf `≥ window_start` |
| **Geteilt zwischen Slots?** | **JA — beide Slots nutzen denselben `get_jitter_today()`-Wert** (gemeinsam pro Tag) |

**Implikation:** Der Jitter wird einmal pro Tag gerollt und für beide Slot-Berechnungen verwendet. Das ist beabsichtigt (User-Setup-Konsistenz: ein User-„Schicksal" pro Tag, nicht zwei separate Jitters), erzeugt aber eine schwache Korrelation zwischen Slot-A- und Slot-B-Plan-Beginn. Für die Phase 11.1 nicht relevant, aber als Test-Hint zu beachten: Tests sollten den Jitter explizit deterministisch setzen (z.B. `monkeypatch.setattr(peakshare_provider, "_jitter_today", 0)`).

### `get_discharge_plan` Cache-Lifecycle (`peakshare.py:308-432`)

**Signatur (Phase 11 final):**
```python
def get_discharge_plan(
    self,
    community: str,
    available_kwh: float,
    discharge_power_kw: float,
    sunset_time: datetime | None,
    now: datetime,
    discharge_start_lower_bound: datetime | None = None,
    next_sunrise: datetime | None = None,
    *,
    slot: str = "a",                     # Phase 11
    window_start: datetime | None = None, # Phase 11 — Slot-Override
    window_end: datetime | None = None,   # Phase 11 — Slot-Override
) -> tuple[datetime, datetime] | None
```

**Lifecycle-Sequenz:**

```
async_run_cycle:
  1. async_fetch()                        ← einmal pro Cycle, AKTUALISIERT _cache, INVALIDIERT _discharge_plan wenn fresh data
  2. snap = _gather_snapshot()
  3. _evaluate(snap):
       _should_discharge → Dispatcher
         _evaluate_slot_a(snap):
            ⇒ get_discharge_plan(..., slot="a", window_start=..., window_end=...)
              ↳ if _discharge_plan_date == today_str: return _discharge_plan["a"]   ← cached
              ↳ else: compute via find_discharge_window, store, return
         _evaluate_slot_b(snap):
            ⇒ get_discharge_plan(..., slot="b", window_start=..., window_end=...)
              ↳ same pattern, different slot key
```

**Kritische Eigenschaft des Tageslocks:**
```python
# peakshare.py:347-349
if self._discharge_plan_date == today_str:
    return self._discharge_plan.get(slot)
```

Das `_discharge_plan_date` ist **gemeinsam** für beide Slots. Sobald **EINER** der Slots heute berechnet wurde, ist `_discharge_plan_date == today_str`, und der **andere** Slot bekommt beim nächsten Aufruf nur `_discharge_plan.get(slot) == None` zurück — auch wenn er noch nicht berechnet wurde!

**Konsequenz für Phase 11.1:** Der erste `get_discharge_plan(slot=...)`-Aufruf des Tages MUSS für **beide Slots** Pläne berechnen, ODER der Cache-Lookup muss umgeschrieben werden. Andernfalls kann nur der erste angefragte Slot je einen PeakShare-Plan haben — der zweite Slot bekommt immer `None` (= falsche Fallback-Aktivierung).

**Recommendation (siehe Plan-Cache-Lifecycle-Sektion unten):** Cache-Logik in `get_discharge_plan` erweitern auf "berechne nur, wenn `_discharge_plan_date != today_str ODER `_discharge_plan[slot] is None`" — d.h. lazy-pro-Slot statt lazy-pro-Tag.

### `find_discharge_window` Edge Cases

| Edge Case | Verhalten | Test-Bedarf |
|-----------|-----------|------------|
| `window_start ≥ window_end` | `get_discharge_plan` setzt `_discharge_plan[slot] = None`, lockt Tag, liefert `None` (peakshare.py:392-401) | Slot-Sommer-Edge-Case (b_start ≥ b_end) — bereits Slot-B-Logik |

## Slot-Window-Berechnung (genau)

### Slot A — Window-Grenzen

```python
# In _evaluate_slot_a vor dem PeakShare-Aufruf:
a_start_today = snap.now.replace(
    hour=self._discharge_a_start_h, minute=self._discharge_a_start_m,
    second=0, microsecond=0,
)

# Past-Midnight-Phase-Detection (existing logic, optimizer.py:1110-1112):
is_past_midnight_phase = (
    snap.now.hour < 12 and self._discharge_a_start_h >= 12
)

# Window-Start: bei past-midnight ist das ECHTE a_start gestern; sonst heute.
if is_past_midnight_phase:
    a_window_start = a_start_today - timedelta(days=1)
else:
    a_window_start = a_start_today

# Window-Ende:
if self._enable_slot_b:
    # Dual-Mode: 5min vor Slot-B-Start (Mutual Exclusion)
    b_start = snap.now.replace(
        hour=self._discharge_b_start_h, minute=self._discharge_b_start_m,
        second=0, microsecond=0,
    )
    # b_start auf morgen verschieben wenn now nachmittags + b_start vormittags
    # (existing logic, optimizer.py:1126-1127):
    if self._discharge_b_start_h < 12 and snap.now.hour >= 12:
        b_start = b_start + timedelta(days=1)
    a_window_end = b_start - timedelta(minutes=5)

Ein PeakShare-Hour-Eintrag `2026-12-21 22:00` (gestern) wäre sonst weg, obwohl die Slot-A-Sitzung gerade läuft.

## Slot-spezifisches `available_kwh`

### Formeln

```python
# Im Optimizer, beim Aufruf von get_discharge_plan(...):

# Slot A:
if self._enable_slot_b:
    a_min_soc = min_soc + self._discharge_a_reserve_pct
    available_kwh_a = (snap.battery_soc - a_min_soc) / 100 * snap.battery_capacity_kwh
else:
    # A-only: keine Reserve-Aufschlag, Slot A nutzt komplettes Budget
    available_kwh_a = (snap.battery_soc - min_soc) / 100 * snap.battery_capacity_kwh

# Slot B:
# Die "Reserve" ist genau das, was Slot A für Slot B übrig gelassen hat.
# Mit Default-Wechsel reserve_pct=5 heißt das: ~0.5 kWh bei 10kWh-Batterie.
available_kwh_b = (self._discharge_a_reserve_pct / 100) * snap.battery_capacity_kwh
```

### Implikation des Default-Wechsels 15 → 5

| reserve_pct | Bei 10 kWh Batterie | Slot-B `required_hours` bei 5 kW Power |
|-------------|---------------------|----------------------------------------|
| 15 % (alt) | 1.5 kWh | `ceil(1.5 / 5.0)` = 1 |
| 5 % (neu) | 0.5 kWh | `ceil(0.5 / 5.0)` = 1 |

Bei beiden Werten ist `required_hours = 1` für eine 10kWh-Batterie + 5kW-Discharge. Slot B sucht also einen 1-Stunden-Block in seinem Window. Bei größeren Batterien (z.B. 20kWh):
- 15 %: 3.0 kWh → `required_hours = 1` (ceil 0.6 = 1)
- 5 %: 1.0 kWh → `required_hours = 1` (ceil 0.2 = 1)

In der Praxis ist `required_hours` für Slot B fast immer 1, weil 5 % einer typischen Hausbatterie sehr wenig ist. Das ist OK — Slot B ist Tropfen-auf-den-heißen-Stein für "EEG-Spitze früh morgens", nicht der Haupt-Slot.

`[ASSUMED]` Bei sehr großen Batterien (50+ kWh) und niedriger Discharge-Power (<3 kW) könnte `required_hours = 2` werden — das ist aber atypisch für EEG-Setups (kleine Hausanlagen). Test-Hint: Edge-Case mit `battery_capacity=50, discharge_power=3, reserve_pct=5` → `available_kwh_b=2.5, required_hours=1`.

### Slot-A-Available-Sanity-Check

Wenn `snap.battery_soc ≤ a_min_soc`, dann ist `available_kwh_a ≤ 0` → `find_discharge_window` liefert sofort `None` (peakshare.py:71). Das ist OK: in dem Fall greift sowieso der SOC-Block in `_evaluate_slot_a` (Z. 1143-1148, `REASON_SLOT_A_RESERVE_REACHED`) — PeakShare-Aufruf ist überflüssig, aber nicht schädlich. Frühzeitige Sanity-Prüfung im Optimizer kann den Aufruf einsparen.

## Plan-Cache-Lifecycle (kritischer Punkt)

### Heutiger Stand

```python
# peakshare.py:344-349 — heute:
today_str = now.strftime("%Y-%m-%d")
if self._discharge_plan_date == today_str:
    return self._discharge_plan.get(slot)
```

Das `_discharge_plan_date` wird beim **ersten** `get_discharge_plan(...)`-Call gesetzt (Z. 415-416), egal welcher Slot. Beim **zweiten** Call (anderer Slot, gleicher Tag) wird der Cache-Lookup positiv (`_discharge_plan_date == today_str`) — und der Code liefert sofort den (möglicherweise leeren) `_discharge_plan[slot]`-Eintrag zurück, **ohne** ihn zu berechnen.

### Problem-Szenario

```
Cycle 1 — now=22:00:
  _evaluate_slot_a → get_discharge_plan(slot="a", window=[20:00, 02:55])
    ↳ _discharge_plan_date != today → COMPUTE
    ↳ _discharge_plan["a"] = (22:00, 23:00)
    ↳ _discharge_plan_date = today
    ↳ return (22:00, 23:00)   ← Slot A bekommt Plan ✓

  _evaluate_slot_b → get_discharge_plan(slot="b", window=[03:00, 06:25])
    ↳ _discharge_plan_date == today → CACHE HIT
    ↳ return _discharge_plan.get("b") == None   ← Slot B bekommt FALSE NEGATIVE
```

**Folge:** Slot B fällt für den Rest des Tages permanent auf Fixzeit zurück, obwohl er einen PeakShare-Plan haben sollte.

### Recommendation: Per-Slot-Lazy-Compute

```python
# peakshare.py — vorgeschlagene Änderung in get_discharge_plan:
today_str = now.strftime("%Y-%m-%d")

# Neu: Cache pro Slot, nicht pro Tag.
# Wenn der Tag wechselt, ALLE Slots invalidieren.
if self._discharge_plan_date != today_str:
    self._discharge_plan = {"a": None, "b": None}
    self._discharge_plan_date = today_str

# Wenn der Slot heute schon berechnet wurde (auch None-Resultat), liefere ihn.
if slot in self._discharge_plan and self._discharge_plan_date == today_str:
    # ABER: nur wenn er ECHT berechnet wurde, nicht weil ein anderer Slot heute computed hat.
    # → wir brauchen ein eigenes "computed-Set" zusätzlich:
    if slot in self._discharge_plan_computed_today:
        return self._discharge_plan[slot]

# ... compute path ...
self._discharge_plan[slot] = plan
self._discharge_plan_computed_today.add(slot)
return plan
```

**Alternative (einfacher):** Eine separate „Compute-Tracking-Set" einführen:

```python
# In __init__:
self._discharge_plan_computed_dates: dict[str, str | None] = {"a": None, "b": None}

# In get_discharge_plan, Cache-Hit-Bedingung:
if self._discharge_plan_computed_dates.get(slot) == today_str:
    return self._discharge_plan.get(slot)

# Nach Compute:
self._discharge_plan[slot] = plan
self._discharge_plan_computed_dates[slot] = today_str
```

Damit wird der Cache pro Slot getrennt invalidiert. `_discharge_plan_date` (gemeinsam) wird nicht mehr für die Cache-Hit-Logik genutzt — kann entfernt oder als zusätzlicher Touch-Wert behalten werden.

**Empfehlung Plan 11.1-01:** Variante 2 (zwei dicts) implementieren. Test in `test_dual_window.py::TestPeakShareSlotIntegration::test_slot_a_then_slot_b_both_computed` deckt das ab.

### Async-Fetch-Invalidate bleibt korrekt

```python
# peakshare.py:243-250 — heute:
self._discharge_plan = {"a": None, "b": None}
self._discharge_plan_date = None
```

Bei Frischer-Daten-Eingang werden BEIDE Slot-Plans verworfen. Das ist korrekt und bleibt unverändert. Mit dem neuen `_discharge_plan_computed_dates` muss der Reset entsprechend ergänzt werden:

```python

self._discharge_plan_date = None
self._discharge_plan_computed_dates = {"a": None, "b": None}
```

## Mutual-Exclusion-Clamp (Slot A vs Slot B)

### Wo wirkt der Clamp?

**Antwort: Im `window_end`-Argument an `find_discharge_window`.**

`find_discharge_window` clampt `end_time` automatisch auf `window_end` (peakshare.py:128-129):
```python
if end_time > window_end:
    end_time = window_end
```

Wenn wir aus `_evaluate_slot_a` mit `window_end = b_start − timedelta(minutes=5)` aufrufen, ist die 5-Minuten-Pause **per Konstruktion** garantiert — keine Post-Processing-Clamp im Optimizer nötig.

### Edge-Case: `start_time` so spät, dass clamp `end_time = start_time`?

Theoretisch könnte der Sliding-Window-Algorithmus `best_start = N` finden, sodass `start_time + required_hours > window_end`. Dann wird `end_time` auf `window_end` geklemmt → Plan-Window ist effektiv kürzer als `required_hours`.

Beispiel: `available_kwh = 5`, `discharge_power = 5`, `required_hours = 1`, `window_end = b_start − 5min = 02:55`. Sliding-Window könnte `best_start` auf 02:30 setzen → `end_time` würde auf 02:55 geklemmt (statt 03:30). Slot A entlädt also nur 25 Minuten statt 60 Minuten.

**Beurteilung:** Das ist akzeptabel. Der Inverter macht das `set_discharge`-Kommando in beide Phasen identisch („leistet Leistung X bis Stop"); der nächste Cycle sieht dann `now > end_time` → Stop-Kommando vor `b_start − 5min`. Mutual Exclusion bleibt strikt eingehalten.

**Test:** `test_slot_a_plan_clamped_at_b_start_minus_5min` — verifiziert, dass `find_discharge_window(window_end=b_start-5min)` niemals ein Resultat mit `result[1] > b_start - 5min` liefert.

    if peakshare_plan is not None:
        plan_start, plan_end = peakshare_plan
        if snap.now < plan_start:
            return (False, [], [REASON_PEAKSHARE_BEFORE_WINDOW], False)
        if snap.now >= plan_end:
            return (False, [], [REASON_PEAKSHARE_WINDOW_EXPIRED], False)

    # Existing: SOC-Schwelle (Reserve-aware)
    a_reserve = self._discharge_a_reserve_pct if self._enable_slot_b else 0
    a_min_soc = min_soc + a_reserve
    is_reactivation = (
        self._slot_a_activated_date is not None
        and self._last_active_slot != "A"
    )
    effective_min_soc = a_min_soc + (5 if is_reactivation else 0)

    if snap.battery_soc <= effective_min_soc:
        blocked_by = []
        if is_reactivation:
            blocked_by.append(REASON_HYSTERESIS_STRICT)
        blocked_by.append(REASON_SLOT_A_RESERVE_REACHED)

    passing = []
    if is_reactivation:

    if peakshare_plan is not None:
        passing.append(REASON_PEAKSHARE_WINDOW_ACTIVE)
    passing.append(REASON_SOC_ABOVE_MIN)
    passing.append(REASON_SLOT_A_ACTIVE)
    return (True, passing, [], is_reactivation)
```

**Branching-Pattern (entspricht `_evaluate_legacy_window:1346-1373`):**
- PeakShare-Plan vorhanden → Window-Status prüfen via `plan_start`/`plan_end` (BEFORE/EXPIRED/ACTIVE).
- PeakShare-Plan `None` → vorhandene Fixzeit-Window-Prüfung greift (`a_start_today`, `a_end_cap`).

## Reasons-Strategie

### Optionen

**Option A (RECOMMENDED): Bestehende `REASON_PEAKSHARE_*`-Keys wiederverwenden**

**Pro:**

- Telemetrie-Backend und Activity-Log brauchen keine neuen Mappings.
- Slot-Information kommt bereits über `REASON_SLOT_A_ACTIVE` / `REASON_SLOT_B_ACTIVE` (gleichzeitig in der `passing`-Liste).
- Konsistent mit Legacy-Pfad (`_evaluate_legacy_window` Z. 1363-1368) — gleiche Keys für gleiche Semantik.

**Contra:**
- Bei reiner Reasons-Inspektion ist nicht direkt klar, welcher Slot aktiv ist — aber das ist über `discharge_active_slot` ohnehin sauber maschinenlesbar.

**Option B: Neue slot-spezifische Reasons (`peakshare_slot_a_window_active`, `peakshare_slot_b_window_active`, ...)**

**Pro:**
- Reasons-Liste ist auch ohne `discharge_active_slot` selbsterklärend.

- 6 neue Keys (3 status × 2 slots), 6 neue `REASON_LABELS_DE`-Einträge.

**Option A — bestehende Keys wiederverwenden.** `discharge_active_slot` macht die Slot-Disambiguierung maschinenlesbar; Activity-Log-Heartbeats können Slot+PeakShare durch Kombination der vorhandenen Felder rendern. Telemetrie-Backend bleibt schemata-stable.

## Fallback-Strategie (PeakShare nicht verfügbar)

Drei orthogonale Bedingungen, die einen Slot in den Fixzeit-Pfad zurückwerfen:

| Bedingung | Wo geprüft? | Verhalten |
|-----------|-------------|-----------|
| `enable_peakshare = False` (User-Setting) | `_evaluate_slot_*` vor PeakShare-Aufruf | `peakshare_plan = None` → Fixzeit-Pfad |
| PeakShare-Cache leer (`_cache is None`) — z.B. erster Cycle, API down | `peakshare.get_discharge_plan` Z. 352-353 | Liefert `None` → Fixzeit-Pfad |
| Datenabdeckung fehlt (Hours-Liste deckt Slot-Window nicht) | `find_discharge_window` Z. 92-93 (`len(eligible) < required_hours`) | Liefert `None` → Plan wird gecacht als `None`, Fixzeit-Pfad |
| Sommer-Edge-Case (`window_start ≥ window_end`) | `peakshare.get_discharge_plan` Z. 392-401 | Plan wird als `None` gecached, Fixzeit-Pfad |

**Per-Slot-Unabhängigkeit:** Die `get_discharge_plan(slot=...)`-API liefert Plan oder `None` pro Slot. Slot A kann einen PeakShare-Plan haben, Slot B `None` → Slot A nutzt PeakShare, Slot B nutzt Fixzeit. Mit dem oben empfohlenen Per-Slot-Compute-Tracking ist das auch beim ersten-Slot-zuerst-Compute sichergestellt.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Sliding-Window-Suche pro Slot | Eigener Algorithmus, separate Schleife für Slot A/B | `peakshare.find_discharge_window(window_start=..., window_end=...)` zweimal aufrufen | Algorithmus inkl. Contiguity-Check, Jitter-Anwendung, End-Time-Clamp ist verifiziert (peakshare.py:44-131) und durch `tests/test_peakshare.py` abgedeckt |
| Mutual-Exclusion-Clamp Slot-A-Plan ≤ b_start − 5min | Post-Processing im Optimizer (`if plan_end > b_start - 5min: plan_end = ...`) | Den Clamp via `window_end=b_start - timedelta(minutes=5)` an `find_discharge_window` weitergeben | `find_discharge_window` Z. 128-129 macht den Clamp atomar — kein Risiko, dass Caller den Post-Process vergisst |
| Pro-Slot-Cache-Invalidierung | Eigene Tracking-Logik im Optimizer | Erweiterung von `peakshare.PeakShareProvider` mit `_discharge_plan_computed_dates` | Cache lebt im Provider; Optimizer ruft nur `get_discharge_plan(slot=...)` auf — Single Source of Truth |
| Available-kWh-Aufteilung | Eigene komplexe Demand-weighted Berechnung | **Statisch:** A bekommt `(soc - a_min_soc) * cap`, B bekommt `reserve_pct * cap` | Locked Decision #2: Slot A bevorzugt, demand-weighted ist Backlog. Keep it simple. |
| Slot-Window-Past-Midnight-Logik | Eigene Day-Shift-Mathematik | Existierende Logik in `_evaluate_slot_a` (Z. 1110-1112) und `_evaluate_slot_b` (Z. 1187-1188) wiederverwenden | Past-Midnight ist bereits gelöst — neuer Code muss nur `a_window_start` korrekt um einen Tag zurückprojizieren |

**Key insight:** Phase 11.1 ist eine **Verdrahtungs-Phase**. Jedes Hand-Rolling deutet auf einen Mismatch zur existierenden Phase-11-Architektur hin.

## Common Pitfalls

### Pitfall 1: Cache-Tageslock blockiert zweiten Slot
**What goes wrong:** Erster Slot-Aufruf setzt `_discharge_plan_date = today_str`. Zweiter Slot-Aufruf trifft Cache-Hit (`_discharge_plan_date == today_str`), bekommt aber `_discharge_plan.get("b") == None`, weil der Slot nie berechnet wurde.
**Why it happens:** `_discharge_plan_date` ist gemeinsam für beide Slots — siehe Sektion **Plan-Cache-Lifecycle**.
**How to avoid:** Per-Slot-Compute-Tracking via `_discharge_plan_computed_dates: dict[str, str|None]` einführen.
**Warning signs:** 24h-Sim-Test zeigt: Slot A hat PeakShare-Plan, Slot B fällt komplett auf Fixzeit zurück (auch wenn Daten da sind).
**Test:** `TestPeakShareSlotIntegration::test_both_slots_compute_independently`.

### Pitfall 2: Past-Midnight-Phase überspringt PeakShare-Hours von gestern
**What goes wrong:** Slot A startet 20:00 (gestern). PeakShare-Hours sind UTC-Timestamps, z.B. `2026-12-20T22:00:00Z`. Wenn `_evaluate_slot_a` jetzt um 02:30 läuft (heute) und `window_start = a_start_today` (= 2026-12-21 20:00) setzt, sind die gestrigen Hours außerhalb `[window_start, window_end)` → keine Eligibility → `find_discharge_window` liefert `None`.
**Why it happens:** `is_past_midnight_phase` setzt `a_start_today` falsch zur Window-Bound-Berechnung. Korrekt: bei past-midnight muss `a_window_start = a_start_today - timedelta(days=1)`.
**How to avoid:** Window-Start abhängig von `is_past_midnight_phase` setzen (siehe Pseudocode in `_evaluate_slot_a`-Sektion).
**Warning signs:** Slot A bekommt nachts ab Mitternacht plötzlich `peakshare_plan = None`, obwohl er tagsüber + abends einen Plan hatte.
**Test:** `TestPeakShareSlotA::test_past_midnight_uses_yesterday_window_start`.

### Pitfall 3: Slot B `available_kwh` zu klein → required_hours-Mismatch
**What goes wrong:** Mit `reserve_pct = 5` und 5kWh-Batterie ist `available_kwh_b = 0.25 kWh`, `required_hours = ceil(0.25/5.0) = 1`. PeakShare findet einen 1h-Block. Der Inverter entlädt aber 5 kW × 1h = 5 kWh, nicht 0.25 kWh — **massive Diskrepanz**.
**Why it happens:** `find_discharge_window` plant nach `required_hours = ceil(available/power)`, nicht nach echtem Energie-Limit. Der Inverter kennt das `available_kwh` nicht.
**How to avoid:** `available_kwh_b` erst auf einen sinnvollen Mindestwert clampen, oder den Plan über die SOC-Schwelle in `_evaluate_slot_b` natürlich beenden lassen (Slot B endet sobald `soc <= min_soc`). Letzteres ist bereits durch die existierende SOC-Logik garantiert.
**Warning signs:** Slot B läuft volle 1h, obwohl er rechnerisch nur 3 Minuten Energie hatte → SOC fällt unter `min_soc` → nächster Cycle blockt mit `REASON_SOC_BELOW_MIN`.
**Beurteilung:** Akzeptabel, weil die SOC-Schwelle das natürlich begrenzt. Tests sollten aber prüfen, dass kein „Über-Discharge" passiert.

### Pitfall 4: Jitter über Slot-Grenze schiebt Plan-Start vor `b_start`
**What goes wrong:** Slot-B-Plan wird mit `window_start = b_start = 03:00` aufgerufen. PeakShare findet besten Block ab 03:00. Jitter `−45 Minuten` würde `start_time` auf 02:15 setzen → clamp auf `window_start = 03:00` (peakshare.py:124-125).
**Why it happens:** Der Jitter-Clamp ist bereits implementiert. KEIN Pitfall — nur zur Bestätigung dokumentiert.
**Test:** `TestPeakShareSlotB::test_negative_jitter_clamped_to_b_start`.

### Pitfall 5: Slot A Plan-Ende > b_start − 5min trotz `window_end`-Clamp?
**What goes wrong:** Theoretisch könnte ein Bug in `find_discharge_window` den End-Time-Clamp übergehen (z.B. Off-by-one).
**Why it happens:** Defense-in-Depth ist sinnvoll.
**How to avoid:** Test im Plan 11.1-01: `assert plan_a[1] <= b_start - timedelta(minutes=5)` für eine breite Range an `b_start`-Werten.
**Warning signs:** Activity-Log zeigt Slot-A-aktiv noch nach `b_start`.

### Pitfall 6: PeakShare-Aktivierung deckt Hysterese-Aufschlag NICHT ab
**What goes wrong:** PeakShare-Plan sagt „aktiv ab 22:00" → Slot A wird aktiviert. Im selben Cycle endet Slot A wegen SOC-Reserve. Im nächsten Cycle ist `_slot_a_activated_date` gesetzt, `_last_active_slot != "A"` → Hysterese-Aufschlag +5 % greift. PeakShare-Plan ist immer noch aktiv → Slot A würde reaktivieren, aber mit höherer SOC-Schwelle.
**Why it happens:** Korrektes Verhalten — das ist nicht-Buggy.
**How to verify:** Test prüft, dass die Hysterese-Logik auch im PeakShare-Window-Aktiv-Pfad greift.
**Test:** `TestPeakShareSlotA::test_hysteresis_strict_with_peakshare_active`.

### Pitfall 7: `_discharge_detail_status` zeigt Slot-A-Plan auch bei aktivem Slot B
**What goes wrong:** `_discharge_detail_status` (optimizer.py:871-882) lädt heute hartkodiert `_discharge_plan["a"]` → bei Slot-B-Aktivierung zeigt das Status-Card Slot-A-Plan-Zeiten. Verwirrend für User.
**Why it happens:** Code wurde in Plan 11-02 für Single-Slot-A vorbereitet, nicht für aktiven Slot.
**How to avoid:** `_discharge_detail_status` muss `active_slot` von `_evaluate` durchgereicht bekommen — dann lädt es `_discharge_plan[active_slot or "a"]`.
**Test (in Plan 11.1-02):** `test_discharge_detail_status_shows_slot_b_plan_when_b_active`.

# optimizer.py — _evaluate_slot_a, erweitert um PeakShare-Lookup
def _evaluate_slot_a(
    self, snap: Snapshot, min_soc: float
) -> tuple[bool, list[str], list[str], bool]:
    a_start_today = snap.now.replace(
        hour=self._discharge_a_start_h,
        minute=self._discharge_a_start_m,
        second=0, microsecond=0,
    )
    is_past_midnight_phase = (
        snap.now.hour < 12 and self._discharge_a_start_h >= 12
    )
    if not is_past_midnight_phase and snap.now < a_start_today:
        return (False, [], [REASON_BEFORE_SLOT_A], False)

    # Slot-Window-Ende berechnen (für PeakShare und Fixzeit-Pfad)
    if self._enable_slot_b:
        b_start = snap.now.replace(
            hour=self._discharge_b_start_h,
            minute=self._discharge_b_start_m,
            second=0, microsecond=0,
        )
        if self._discharge_b_start_h < 12 and snap.now.hour >= 12:
            b_start = b_start + timedelta(days=1)
        a_end_cap = b_start - timedelta(minutes=5)
        if snap.now >= a_end_cap:
            return (False, [], [REASON_SLOT_A_RESERVE_REACHED], False)
    else:
        a_end_cap = compute_hard_cutoff(snap.now, snap.sunrise)

    # SOC-Schwelle (Reserve-aware) — vorgezogen für PeakShare-available_kwh
    a_reserve = self._discharge_a_reserve_pct if self._enable_slot_b else 0
    a_min_soc = min_soc + a_reserve

    # PeakShare-Plan-Lookup (Phase 11.1)
    peakshare_plan = None
    if self._enable_peakshare and self._peakshare is not None:
        available_kwh = (snap.battery_soc - a_min_soc) / 100 * snap.battery_capacity_kwh
        if available_kwh > 0:
            a_window_start = (
                a_start_today - timedelta(days=1)
                if is_past_midnight_phase else a_start_today
            )
            peakshare_plan = self._peakshare.get_discharge_plan(
                self._peakshare_community,
                available_kwh,
                self._discharge_power_kw,
                snap.sunset_today,
                snap.now,
                discharge_start_lower_bound=a_window_start,
                next_sunrise=snap.sunrise,
                slot="a",
                window_start=a_window_start,
                window_end=a_end_cap,
            )

    # PeakShare-Window-Status-Branch
    if peakshare_plan is not None:
        plan_start, plan_end = peakshare_plan
        if snap.now < plan_start:
            return (False, [], [REASON_PEAKSHARE_BEFORE_WINDOW], False)
        if snap.now >= plan_end:
            return (False, [], [REASON_PEAKSHARE_WINDOW_EXPIRED], False)
        # Window aktiv → SOC-Check unten

    # Pro-Slot-Hysterese
    is_reactivation = (
        self._slot_a_activated_date is not None
        and self._last_active_slot != "A"
    )
    effective_min_soc = a_min_soc + (5 if is_reactivation else 0)

    if snap.battery_soc <= effective_min_soc:
        blocked_by: list[str] = []
        if is_reactivation:
            blocked_by.append(REASON_HYSTERESIS_STRICT)
        blocked_by.append(REASON_SLOT_A_RESERVE_REACHED)
        return (False, [], blocked_by, is_reactivation)

    passing: list[str] = []
    if is_reactivation:
        passing.append(REASON_HYSTERESIS_STRICT)
    if peakshare_plan is not None:
        passing.append(REASON_PEAKSHARE_WINDOW_ACTIVE)
    passing.append(REASON_SOC_ABOVE_MIN)
    passing.append(REASON_SLOT_A_ACTIVE)
    return (True, passing, [], is_reactivation)
```

def _evaluate_slot_b(
    self, snap: Snapshot, min_soc: float
) -> tuple[bool, list[str], list[str], bool]:

        return (False, [], [REASON_SUNRISE_UNKNOWN], False)

    b_start = snap.now.replace(
        hour=self._discharge_b_start_h,
        minute=self._discharge_b_start_m,
        second=0, microsecond=0,
    )
    if snap.now.hour >= 12 and self._discharge_b_start_h < 12:

    b_end = compute_b_window_end(
        snap.now, snap.sunrise,
        self._discharge_b_end_cap, float(self._morning_start_offset_h),
    )
    if b_end is None:
        return (False, [], [REASON_SUNRISE_UNKNOWN], False)
    if b_start >= b_end:
        return (False, [], [REASON_SLOT_B_PRE_SUNRISE_CUTOFF], False)

    # PeakShare-Plan-Lookup (Phase 11.1)
    peakshare_plan = None
    if self._enable_peakshare and self._peakshare is not None:

            self._discharge_a_reserve_pct / 100
        ) * snap.battery_capacity_kwh

                next_sunrise=snap.sunrise,

                window_start=b_start,
                window_end=b_end,

## Open Questions (RESOLVED)

1. **Soll `_discharge_plan_computed_dates` als Schema-Erweiterung in der persistierten Storage gespeichert werden?**
   - What we know: Heute persistiert `Store` nur `data`, `fetched_at`, `jitter_value`, `jitter_date` — nicht `_discharge_plan` selbst (`peakshare.py:251-258`).
   - What's unclear: Ob das neue `_discharge_plan_computed_dates` persistiert werden muss (Recovery nach HA-Restart) oder ob es OK ist, den Compute beim ersten Cycle nach Restart neu durchzuführen.
   - **RESOLVED:** NICHT persistieren — der Compute ist günstig (Sliding-Window über ~24 Hours-Datapoints), und ein neuer Cycle hat eh frische `_jitter_today`-Werte. Spart Schema-Migration des Persistats. Plan 11.1-01 hält `_discharge_plan_computed_dates` rein im Memory.

2. **Sollte `_discharge_detail_status` (optimizer.py:871-882) auch in Plan 11.1-01 mit angefasst werden, oder bleibt das in 11.1-02?**
   - **RESOLVED:** In 11.1-02 — die Decision-Engine-Änderung in 11.1-01 ist atomar nachvollziehbar; Markdown/Detail-Status-Änderung kann separat gemerged werden, ohne dass User-sichtbares Verhalten zwischen Plans inkonsistent ist. Wave-Trennung 11.1-01 → 11.1-02 ist konsistent zur Plan-Struktur.

3. **Wie verhält sich Slot A, wenn der PeakShare-Plan-Endzeit „zu früh" ist (z.B. Plan endet 22:00, aber Slot-A-User-Erwartung ist „bis SOC fällt")?**
   - **RESOLVED:** Plan-Endzeit ist HARTE Grenze. Nach `plan_end` blockiert `REASON_PEAKSHARE_WINDOW_EXPIRED`. Slot A endet, auch wenn SOC noch hoch ist. Das ist genau der Sinn von PeakShare: nur entladen, wenn die Community das WIRKLICH braucht.
   - Test: `test_slot_a_peakshare_expired_returns_blocked` — verifiziert das.
